# E-commerce Order Analytics Pipeline

> Status: 🚧 In Progress — Day 10-11 / 28 (เริ่ม 2026-08-07)

## Problem

ร้านค้าออนไลน์มีข้อมูล orders, customers, products ไหลเข้ามาทุกวัน แต่ข้อมูลดิบมักมีปัญหา: duplicate record, orphan order (ไม่มี customer จริง), payment ที่ status ไม่ตรงกับ order, ทำให้ทีม business ดูยอดขายผิดหรือ query ยาก

โปรเจกต์นี้สร้าง pipeline ที่ดึงข้อมูล, ตรวจสอบคุณภาพ, แปลงข้อมูล, และส่งออกเป็น serving table ที่ทีม analytics ใช้ตอบคำถามธุรกิจได้ทันที เช่น "ลูกค้ากลุ่มไหนใช้จ่ายเยอะสุดในแต่ละจังหวัด" หรือ "ยอดขายรายวันเทียบกับวันก่อนหน้าเป็นยังไง"

## Architecture (จะเพิ่มขึ้นเรื่อย ๆ ตามที่เรียน)

```
Source (CSV/API) → raw/ → staging/ → serving/
                                          ↓
                                Orchestrated by Airflow (Week 2)
```

รายละเอียดเต็ม (OLTP vs OLAP, ทำไม raw ต้องแยกเก็บ, เลือก file format ยังไง) ดูที่ [`docs/architecture.md`](docs/architecture.md)

Role ของแต่ละเครื่องมือ (cron/script/SQL engine/warehouse) + ทำไมเริ่มจาก batch ไม่ใช่ streaming ดูที่ [`docs/compute_notes.md`](docs/compute_notes.md)

## Trade-offs: ทำไมเริ่มจาก batch

- ข้อมูล order ไม่ต้องการความสดระดับวินาที — สรุปยอดขายรายวัน (refresh วันละครั้ง) ก็ตอบคำถามธุรกิจที่ต้องการได้แล้ว (เช่น "เมื่อวานขายได้เท่าไหร่เทียบกับวันก่อน")
- Batch เขียน/debug/reason ง่ายกว่ามาก — ทุก script ที่เขียนมา (`clean_order.py`, `extract_api.py`, `daily_summary.py`) รันจบแล้วได้ output คงที่ตรวจสอบได้ ต่างจาก streaming ที่ต้องจัดการ ordering, duplicate, checkpoint, late data เพิ่ม (ความซับซ้อนที่ยังไม่คุ้มค่าถ้า business ไม่ได้ต้องการ real-time จริงๆ)
- แนวทางมาตรฐาน: เริ่ม batch → ขยับเป็น micro-batch ถ้าต้องการ latency ต่ำลง → ใช้ streaming จริง (Kafka + stream processor) เฉพาะตอนที่ business case ต้องการ near-real-time เท่านั้น

## Reliability: Idempotency, Incremental Load, Data Quality

### Idempotency (พิสูจน์แล้ว ไม่ใช่แค่ทฤษฎี)

`src/clean_order.py` รันซ้ำกี่รอบก็ได้ผลลัพธ์เดิม ไม่เกิด duplicate — ทดสอบจริงโดยรัน 3 รอบติดกันบนข้อมูลชุดเดิม:

| Run | `dupe_id_check` (order_id ใหม่ที่เจอ) | จำนวนบรรทัดใน `orders_clean.csv` |
|---|---|---|
| 1 (first run, watermark ว่าง) | 19 order_id | 13 (1 header + 12 clean rows) |
| 2 (rerun ทันที) | 0 (ว่างเปล่า — ทุกแถวเก่ากว่า watermark ถูก skip) | 13 (เท่าเดิม) |
| 3 (rerun อีกครั้ง) | 0 | 13 (เท่าเดิม) |

verify เพิ่มเติมว่าไม่มี `order_id` ซ้ำในไฟล์ output (`uniq -d` บนคอลัมน์ `order_id` ได้ผลว่างเปล่า) และไม่มี header แทรกซ้ำกลางไฟล์

### Incremental Load ผ่าน Watermark

- `data/staging/_watermark.txt` เก็บค่า scalar เดียว = `updated_at` มากที่สุดที่เคย process ไปแล้ว (ไม่ใช่ column ในตารางหลัก — เป็นไฟล์ bookmark แยกต่างหาก)
- ทุกรอบที่รัน `clean_order.py`: อ่าน watermark เดิม → skip แถวที่ `updated_at <= watermark` (ประมวลผลเฉพาะข้อมูลใหม่) → หลัง process เสร็จ คำนวณ watermark ใหม่จาก `max(updated_at)` ของรอบนี้ → เขียนทับไฟล์ watermark
- ผลลัพธ์ที่ clean แล้วเขียนแบบ **append** เข้า `orders_clean.csv` (ไม่ใช่ overwrite) เพื่อสะสมข้อมูลจากทุกรอบ พร้อมเช็คว่าไฟล์เคยมีอยู่ก่อนหรือไม่ ก่อนตัดสินใจว่าจะ `writeheader()` ซ้ำหรือไม่

### Backfill (manual, ยังไม่ automate)

ถ้าต้องการ reprocess ข้อมูลทั้งหมดใหม่ (เช่น แก้ validation logic แล้วอยากรันย้อนหลังทั้งชุด): ลบ `data/staging/_watermark.txt` และ `data/staging/orders_clean.csv` แล้วรัน `clean_order.py` ใหม่ — เทียบเท่า full backfill เพราะ watermark กลับไปเป็นค่าต่ำสุด ทุกแถวจะถูก process อีกครั้ง

### Data Quality Checks ที่มีตอนนี้

| Check | Rule | เก็บไว้ใน |
|---|---|---|
| Duplicate `order_id` | เก็บเฉพาะแถวที่ `updated_at` ล่าสุด | `dupe_id_check` |
| Null / N/A | ทุกคอลัมน์ | `null_row` |
| Amount ไม่ใช่ตัวเลข / ติดลบ | parse เป็น float ได้ และ >= 0 | `wrong_num_type` |
| Datetime format ผิด | `created_at`/`updated_at` ต้อง parse เป็น `%Y-%m-%d %H:%M:%S` ได้ | `wrong_date_time` |

## Source

| File | Source | Description |
|---|---|---|
| `data/raw/orders_raw.csv` | Hand-crafted mock data | 20 orders พร้อม intentional dirty-data edge case (comma-formatted amount, null, negative, bad date, duplicate order_id) |

| `data/serving/daily_orders_summary.csv` | Derived from `orders_clean.csv` | สรุปยอดขายรายวัน (`order_date`, `count`, `amount`) ด้วย `src/daily_summary.py` — serving output ตัวแรกของ project |

## How to Run

```bash
# 1. สร้างและเปิดใช้ virtual environment (ครั้งแรกครั้งเดียว)
python -m venv venv
.\venv\Scripts\Activate.ps1        # Windows PowerShell

# 2. ติดตั้ง dependency
python -m pip install -r requirements.txt

# 3. รัน script
python src/clean_order.py          # clean orders_raw.csv -> data/staging/orders_clean.csv
python src/extract_api.py          # extract API -> data/raw/posts_raw.jsonl
python src/daily_summary.py        # aggregate orders_clean.csv -> data/serving/daily_orders_summary.csv
```

## Notes: Retry Strategy

- **ควร retry**: timeout, connection error, HTTP 5xx (500, 502, 503) — เป็น error ฝั่ง server/network ที่มักเป็นปัญหาชั่วคราว retry แล้วอาจสำเร็จ
- **ไม่ควร retry**: HTTP 4xx (400, 401, 404) — เป็น error จาก request เอง (URL ผิด, ไม่มี permission, ข้อมูลไม่มีอยู่จริง) retry ซ้ำก็จะพังเหมือนเดิมทุกครั้ง ต้องแก้ request ก่อน ไม่ใช่ retry
